# Audit — 9 October 2026

Audited baseline: `272ba60` on `main`. Scope: the Next.js app, authentication,
public capture routes, creator review, dashboard queries, Supabase permissions,
free/paid follows, broker metadata and trade ingestion, alert delivery, portfolio
imports and roast calculations, dependency security and CI.

The product is a read-only investor-discovery and update service with fictional
seed profiles. CAS parsing supplies review evidence; it does not independently
verify performance. Broker authorization and production services require separate
operational validation.

## Fixed findings

| Severity | Finding | Change |

| High | Public Supabase insert policies bypassed route validation and allowed arbitrary creator review fields/evidence. | Removed direct public insertion into creator applications, parsed evidence, waitlist, roast leads and follow intents. Validated server routes retain service-role writes. |
| High | Browser clients could assign `active` broker status and arbitrary permissions; saving a preference reset an active connection. | Browser access is read-only. An authenticated RPC saves only the caller's label/preference, preserves provider state, and checks creator eligibility. |
| High | Creator approval performed independent writes, permitting partial role/profile/portfolio changes after failure and duplicates after retries. | Admin-checked database RPC locks the application and creator, commits all writes together, links the accepted application, and returns the original result on retry. Admin roles are preserved. |
| High | Signed payment events were not matched to an application-issued order or its expected amount/currency. Subscription/follow writes were not atomic; replay could restore an intentionally deleted follow. | Private checkout ledger binds user, profile, amount and INR currency. A service-only RPC locks and activates the order once, atomically, after matching all fields. Webhook schemas require captured/paid status. |
| High | Sign-in redirected to unchecked `next` values and decoded them twice; callback checks did not reject backslashes. | One shared local-path validator serves both redirect paths, rejecting external/backslash/control-character redirects. |
| High | Unawaited self-fetches could be terminated after a serverless response, leaving alerts undelivered with no retry records. | Database trigger queues recipients atomically with the alert. Next.js `after()` dispatches delivery; authenticated cron drains pending/failed records. |
| Medium | Concurrent alert paths could overwrite recipient state or duplicate sends; queue/status-write errors were ignored. | Database claims use row locks, ten-minute leases and three-attempt limits; status writes check the claimed attempt and timestamp and surface failures. | Medium | Repeated free follows required an UPDATE blocked by RLS; follower-count trigger also lacked permission to update profiles. | Insert-on-conflict-do-nothing and a narrowly privileged count trigger. Policies reject demo/unpublished follows and fabricated subscription metadata. |

| Medium | Follower dashboard sorted on nonexistent `followers.created_at`, silently returning an empty list; creator dashboard counted rows hidden by follower RLS. | Use `followed_at`, the maintained public follower count, and the primary non-demo portfolio. | Medium | A filled rate-limit map could grow indefinitely and prune hourly limits using an unrelated one-minute window. | Per-key expiration, hard capacity bound and refusal of excess keys without evicting active limits. |
| Medium | Duplicate roast rows diluted single-stock concentration. CSV merging treated an unknown cost as zero. | Merge roast lots using quantity-weighted cost and preserve unknown acquisition dates. CSV cost remains unknown if either lot lacks a price. Reject unclosed CSV quotes. |

## Validation

- `npm test`: 18 passing checks, including executed PostgreSQL migrations and RLS
  under authenticated, anonymous and service roles, approval rollback/idempotency,
  broker authorization, payment matching/replay, queue claiming/consent, malformed
  inputs and mocked provider/audit failures. No emails or payments were sent.
- `npm run lint`: generated route types and TypeScript checks.
- `npm run build`: production build.
- `npm audit --omit=dev --audit-level=moderate`: zero production vulnerabilities.
- Local HTTP smoke checks cover public pages and configuration error handling.

PGlite executes the repository SQL in an isolated PostgreSQL environment with
Supabase-like auth functions and grants. It omits the obsolete `pg_net` migration
and the optional `pgcrypto` extension (UUID generation is built in). It does not
replace testing real Supabase Auth, PostgREST, pg_net or live concurrent sessions.
The test environment has no production Supabase, Resend or Razorpay configuration.

## Remaining work before launch

1. **Billing lifecycle:** checkout is a one-time order, despite subscription UI/table
   naming. Recurrence, entitlement expiry, refund/revocation events and cancellation
   need an explicit model and implementation. Multiple checkout requests before
   activation can still issue multiple orders. Reconcile legacy in-flight orders
   before rollout; the new handler intentionally rejects unrecorded orders.
2. **Alert operations:** the existing daily Vercel cron can delay retries/overflow.
   Each invocation claims up to 500 recipients per transaction and retries up to
   five transactions. Increase worker capacity and schedule for the expected volume,
   add monitoring and dead-letter handling for exhausted attempts. A worker killed
   during its final attempt needs manual reconciliation. Batch idempotency reduces
   duplicates but is not exactly-once delivery: partial audit updates, changed consent,
   changed message content and provider deduplication expiry can alter retry behavior.
3. **Dependencies:** full `npm audit` still reports seven development-chain findings
   through Tailwind 3 (`braces`, `chokidar`, `micromatch`, `fast-glob`,
   `postcss-selector-parser`, `postcss-nested`, Tailwind). The offered automatic fix
   upgrades to Tailwind 4; this requires a deliberate CSS migration and visual QA.
   React 18 support is deprecated in Next.js 16; plan a React 19 migration.
4. **Verification/data accuracy:** CAS evidence needs reviewer SOPs, supported real
   statement fixtures and a clear distinction between holdings review and audited
   performance. The existing performance/drawdown scoring remains heuristic. Live
   benchmark fallback provenance and consistent historical horizons need refinement.
5. **Abuse/privacy:** process-local rate limiting is still best effort across
   serverless instances. Add shared rate limits at scale, request-body limits,
   retention/deletion processing and operational policies for stored CAS text/PII.
   Creator application and parsed evidence insertion still occurs in separate writes;
   the original application retains parsed JSON, but evidence-table failure needs
   reconciliation rather than another signup.
6. **Hosted validation:** apply migrations in staging before code rollout, test real
   auth/admin sessions, Razorpay test webhooks, approved broker adapters, consent,
   email sender configuration and mobile UI. Production was not modified. The
   repository's existing legal/provider launch-review requirements remain outstanding.

## Deployment sequence

Apply the five `20261009*` migrations before deploying the new app routes. Capture
routes require a service-role key; reviewer and broker preference RPCs require the
caller's Supabase auth session. Configure independent webhook, unsubscribe and cron
secrets plus a verified sender. Queue creation starts with new transactions and
never broadcasts historical transactions automatically. Existing subscriptions
remain readable and usable for restoring follows.

Review and reconcile legacy in-flight checkout orders using trusted provider data.
Check legacy failed alert records separately. Follow the README staging checklist
before enabling production payments or promising alert latency.
